# ☕ Coffee Doctor — Ethiopian Coffee Leaf Health Advisor

An AI-powered web app that diagnoses coffee leaf diseases from a photo and
gives farmers a full, professional advisory report — in **English, Amharic
(አማርኛ), Tigrinya (ትግርኛ), and Afaan Oromoo** — with zero hosting cost.

It builds directly on the existing `EthiopianCoffee` ML pipeline
(`backend/src/EthiopianCoffee`): a cascaded **Detector → Disease Classifier**
deep-learning system trained on Ethiopian coffee leaf imagery.

```
📸 Photo  →  🔍 Is it a coffee leaf?  →  🩺 Which disease (or healthy)?  →  📋 Full multilingual expert report
```

---

## What's included

### Backend (`backend/`) — FastAPI
- Reuses your existing training/prediction pipeline untouched.
- `POST /api/v1/predict` — upload an image, get a full structured report.
- `GET /api/v1/diseases` — browse the full disease encyclopedia (no photo needed).
- `GET /api/v1/languages`, `GET /api/v1/health`.
- **Demo mode**: if `final_model/.../model.keras` isn't there yet (i.e. you
  haven't run training), the API still runs end-to-end using a clearly
  labeled placeholder prediction — so you (and anyone testing the app) can
  build/deploy/demo the whole product before training finishes. The moment
  real `.keras` models are dropped into `backend/final_model/`, the API
  automatically switches to real inference — no code changes needed.
- Interactive API docs at `/docs` (Swagger UI, auto-generated by FastAPI).

### Frontend (`frontend/`) — vanilla HTML/CSS/JS (no build step, no framework, no Node needed)
- **4 languages** with full UI translation (not just the diagnosis text):
  English, Amharic, Tigrinya, Afaan Oromoo.
- **Upload from file** (drag-and-drop or file picker) **and live camera
  capture** (front/back camera switch), with a graceful fallback to the
  native mobile camera picker on browsers without camera API support.
- **Comprehensive, professional reports**: overview, symptoms, cause,
  favorable conditions, immediate actions, organic/cultural treatment,
  chemical treatment, prevention plan, economic impact note, and "when to
  consult an expert" — exactly what an agronomist would tell a farmer.
- **Disease Library** — full reference encyclopedia, browsable without
  uploading anything (great for training/education use).
- **Scan history**, stored locally on-device (no account, no server storage).
- **Listen to report** (offline browser text-to-speech) — helpful where
  literacy or screen size is a barrier.
- **Print / Save as PDF** of any report (browser-native, no paid PDF service).
- **Installable PWA** with offline app-shell caching (service worker) — the
  interface still opens on a weak or offline connection.
- **Light/dark theme**, mobile-first, large touch targets.

## Why this stack (given a $0 budget)

| Choice | Reason |
|---|---|
| FastAPI + Uvicorn | Lightweight, async, auto-docs, tiny memory footprint vs. Django — fits free-tier RAM limits. |
| `tensorflow-cpu` | Smaller image / lower RAM than full `tensorflow`; no GPU on free tiers anyway. |
| Vanilla JS frontend (no React/Vue build) | Zero build pipeline, zero Node hosting cost, deploys as static files or is served directly by the same Python process — one free service instead of two. |
| Single Docker image serving API **and** frontend | One free web service (Render/Railway/Fly.io free tier, or Hugging Face Spaces) instead of paying for/managing two separate hosts. |
| PWA + service worker | Offline-friendly for rural/low-connectivity use without any paid CDN. |
| Browser print-to-PDF & Web Speech API | "PDF export" and "voice read-aloud" with **zero** third-party API cost. |

## Running locally

```bash
cd backend
pip install -r requirements.txt --break-system-packages   # or use a venv
uvicorn app.main:app --reload --port 8000
```

Open **http://localhost:8000** — the frontend is served automatically from
the same process (`SERVE_FRONTEND=1` by default), and the API lives under
`/api/v1/...`. No CORS setup needed since it's the same origin.

To develop the frontend only against a separately-running API, open
`frontend/index.html` directly and set `API_BASE` in
`frontend/static/js/app.js` to your API's URL.

### Training the real models

The web layer doesn't change your ML workflow at all:

```bash
cd backend
python main.py train-detector   # -> final_model/coffee_detector/model.keras
python main.py train-disease    # -> final_model/coffee_disease/model.keras
```

Once both `model.keras` files exist under `backend/final_model/`, restart
the API — it leaves demo mode automatically and serves real predictions.

## Deploying for free

**Recommended: one Docker web service** (Render free tier, Railway free
tier, Fly.io free allowance, or Hugging Face Spaces "Docker" SDK).

Run these from the **repository root** (the Dockerfile lives in `backend/`
but needs the root as its build context so it can copy both `backend/` and
`frontend/`):

```bash
docker build -f backend/Dockerfile -t coffee-doctor .
docker run -p 8000:8000 coffee-doctor
```

Steps on **Render** (typical free-tier flow):
1. Push this repo to GitHub.
2. New → Web Service → connect the repo → Environment: **Docker**.
3. Leave the Dockerfile at the repo root path `Dockerfile`... actually this
   project's Dockerfile lives at `backend/Dockerfile` and is built from the
   **repo root** as build context (it copies `backend/` and `frontend/`).
   Set the Dockerfile path to `backend/Dockerfile` and the build context to
   the repository root.
4. Deploy. Render provides a free HTTPS URL automatically (needed for camera
   access in the browser, which requires a secure context).

Steps on **Hugging Face Spaces**:
1. Create a new Space → SDK: **Docker**.
2. Push this repo's contents (with `backend/Dockerfile` and `frontend/`) to
   the Space's git remote.
3. Spaces builds and serves it automatically over HTTPS at no cost.

> ⚠️ Free tiers often spin down after inactivity and cold-start slowly on
> first request — normal and expected at $0 cost. If TensorFlow's RAM use is
> tight on the smallest free tier, keep `tensorflow-cpu` (already set) and
> consider quantizing/exporting a smaller model for production.

## Notes on the language content

The Amharic, Tigrinya, and Afaan Oromoo advisory text was written with AI
assistance to be clear and agronomically accurate for a farmer audience. For
mission-critical or commercial deployment, we recommend a one-time review
pass by a local agronomist or cooperative extension officer per language.
